# AR方式の比較 0.1.0

Roll-by-Blowの前傾時の回転・縮小を切り分ける確認用ページです。ゲーム本体への修正ではありません。目印ありを候補に加え、目印なしの検証も維持するというユーザーの選択に基づき、2方式を別々に確認できます。

Unityのビルドは不要です。AIはブラウザー・カメラ・ARライブラリを実行していません。構文・ファイル参照・依存ファイルの一致を静的に確認した段階で、iPhoneでの成功は未確認です。

## 公開

1. 既存のGitHubリポジトリー `ar-floor-prototype` の公開元に、フォルダー名を **ARTrackingLab** のまま追加します。このフォルダー全体を置いてください。
2. 既存のゲーム用index.htmlやBuildフォルダーには上書きしません。今回はゲーム本体の再ビルド・再公開は不要です。
3. GitHub Pagesの更新が終わったら、iPhoneのSafariで次を開きます。

[比較一覧の公開予定URL](https://ogiyu-tomioka.github.io/ar-floor-prototype/ARTrackingLab/)

このURLは上記の配置後に使える予定のもので、AIが公開・到達確認したURLではありません。別の場所へ置いた場合は、その場所のURLに変わります。ローカルHTMLを直接開く方法ではカメラを使えません。

vendorの中身もすべて必要です。無圧縮のフォルダー全体は約34MBです。各ファイルは[GitHubのブラウザーアップロードの25MiB制限](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository)より小さく、ZIPにまとめる必要はありません。フォルダーの一部だけを公開すると読み込みに失敗します。

## まず目印なし

1. 比較一覧から「目印なしで確認」を開き、「開始」。カメラ・モーションを許可します。
2. いつもの机を映し、スマホをゆっくり前後へ動かします。
3. ボタンが有効になったら「基準を固定」。画面中央の視線の約60cm先に小さな立体と格子を1回だけ固定します。
4. スマホの位置をなるべく変えず、前傾してから元の持ち方へ戻します。同じ持ち方へ戻しても立体が小さくなったままか、勝手な回転が残るかを見ます。
5. 固定から20秒で自動終了します。「診断を保存」を押してください。

このページでは机の自動配置を使いません。立体が机から浮いていても、それ自体は追跡失敗ではありません。主な確認対象は、前傾→元の持ち方へ戻したときの位置・向き・大きさの再現性です。

現行ゲームと同じ8th Wallバイナリを使い、SDKの位置・向き・投影を同じ更新から受け取ります。Unity接続、左右の座標変換、別センサーによるカメラ回転の上書き、点群による机推定、姿勢の遮断処理は使いません。SDK標準の描画ループを使用するため、ゲーム本体の30fps制限とは条件が異なります。改善しても、それだけではどの要因が効いたかは確定しません。

必要な場合だけ、ページ内の詳細からresponsive縮尺でも比較できます。これはメートル単位の縮尺ではないため、自動サイズの要件を満たしたとは扱いません。最初の確認は通常のabsoluteのままで十分です。

## 次に目印あり

1. PCで `marker/print.html` をブラウザーから開き、A4・倍率100%で印刷します。白黒で構いません。
2. 黒い四角の外幅を定規で測ります。白い余白は含めません。想定は12cmですが、印刷後の実測値を使います。
3. 光沢の少ない紙を机に平らに置きます。比較一覧から「目印ありで確認」を開き、測った外幅を入力して「開始」。
4. 黒枠全体を映します。認識すると、その位置に同じ形の立体と格子が出ます。
5. 紙全体が映る範囲で前傾し、元の持ち方へ戻します。見失った場合は立体を隠します。再発見できるかも確認します。
6. 初回発見から20秒で終了します。「診断を保存」を押してください。

目印から位置・向き・縮尺を求めるAR.js 3.4.8の方式です。世界全体の位置推定や独自のセンサー合成は使いません。斜めすぎる、遠すぎる、紙が反る、手や立体で隠れる場合には失敗し得ます。カメラの補正値も一般的なサンプル値なので、実寸の精度は実機評価が必要です。安定性・発熱・必要な印刷サイズについて、現在の方式より良いと確認したわけではありません。

## 報告してほしいこと

- それぞれの診断JSON。
- 元の持ち方に戻したとき、回転・縮小・机からのずれが残ったか。
- 目印ありでは、遊びたい前傾角度まで紙全体を映せたか。

2方式を同時に開いてカメラを使わず、一方を終了してからもう一方を開始してください。どちらも開始から最大60秒、基準固定・初回発見後は20秒で終了します。短い確認に留め、途中でも終了できます。

診断にはカメラ映像や写真を含めません。姿勢・投影・固定物の大きさ・追跡状態・端末情報を記録し、終了後にも残します。ゲームの捕獲記録や設定を読み書きしません。

## 結果による次の判断

| 結果 | 次に進めること |
|---|---|
| 目印なしの単体表示は安定 | 同じSDK・同じ縮尺のまま30fps制限→Unity接続→自動配置の順で戻し、どの段階で崩れるか確認する |
| absoluteで崩れるがresponsiveは安定 | 縮尺推定の関与を調べる。机と同じ大きさに見えるだけで実寸が正しいとは扱わない |
| 目印なし単体でも同様に崩れる | Unityだけの問題とは考えにくい。SDKとSafari・端末・机・操作の組み合わせを追加切り分けする |
| 目印ありで操作範囲を保ちつつ安定 | ゲームとつなぐ候補にする。先に追跡、次に送風・物理・捕獲を確認する |
| 目印を映し続ける操作が難しい | 大きな印刷・複数の目印・別方式を検討する。傾ける操作や半歩の条件を勝手に削らない |

この比較だけでは、机の輪郭・自動サイズ・半歩の操作・ゲーム負荷下の熱・長時間追跡は合格にしません。まずARの基礎が成立するかを確認します。
